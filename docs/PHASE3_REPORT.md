# 第三阶段报告：后端服务

日期：2026-10-09　分支：`phase3/backend`（基于 `phase2/core-contracts`）

## 1. 本阶段完成了什么

仓库改成了 pnpm 多包结构：

| 目录 | 内容 |
|---|---|
| `packages/shared` | 合约 ABI（从 Foundry 编译结果生成）、费率与分配计算的 TypeScript 镜像、财务报告校验（zod）与报告哈希 |
| `packages/db` | Prisma 数据库结构与迁移（PostgreSQL 16，`app` / `chain` / `compliance` 三个 schema） |
| `apps/worker` | 链上事件索引器、链重组回滚、对账 |
| `apps/api` | NestJS REST 接口，路径前缀 `/api/v1` |

### 索引器（`apps/worker`）

- 只处理已确认的区块（默认落后最新块 15 个，可配置）。
- 每个事件原样存入 `chain.event`，同一个数据库事务里更新项目、募集、认购、持仓、报告、分配、角色、投资资格等读模型。
- 新项目由工厂部署后自动加入监听列表。
- 链重组：每次先核对上次处理到的区块哈希，不一致就回退到仍然有效的区块，删除之后的事件，再从事件重建所有读模型。
- 对账：把数据库里的持仓、总量、未领取金额与链上合约状态逐项比对，有差异就记录问题；有未解决问题时，后台拒绝准备新的分配。
- 多实例运行时用 Redis 租约保证只有一个索引器在写。

### API（`apps/api`）

- 登录：以太坊签名登录（SIWE）。nonce 存 Redis，5 分钟有效、只能用一次，核对域名和链 ID。登录成功后用 httpOnly Cookie 保存会话。
- 公开接口：健康检查、项目列表、项目详情（含状态历史、募集条款、费率档位）、已批准的财务报告、分配批次、报告哈希核验、合约地址。
- 投资者接口：投资资格、持仓与占比、认购记录（含是否可退款）、每批分配明细与是否已领取。
- 管理接口：
  - 后台权限要同时满足两点：数据库里登记为员工，且钱包在链上确实持有对应角色。
  - 创建项目草稿、提交财务报告（校验收入 − 支出 − 储备 = 可分配，计算哈希）、审核报告（提交人不能审核自己）、分配预览和准备分配交易、对账结果、角色列表、操作日志。
  - 所有“准备交易”只返回未签名的交易数据，由员工钱包或多签签名。服务器从不持有私钥。
- KYC 回调：校验 HMAC 签名、5 分钟时间窗口、防重放。服务商还没选定，目前只接受 TEST-ONLY 的模拟服务商，并且生产环境下会拒绝。

## 2. 测试结果（实际运行）

`DATABASE_URL=<测试库> pnpm test`，测试用真实的 PostgreSQL 16 和 Redis 7：

| 包 | 测试数 | 结果 |
|---|---|---|
| `packages/shared` | 8 | 全部通过（含 2,000 轮随机测试：资金池守恒、余数小于持有人数，以及 TOKENOMICS §4.4 例子） |
| `apps/api` | 19 | 全部通过（端到端，supertest） |
| `apps/worker` | 5 | 全部通过（在本地 anvil 链上用第二阶段的部署脚本部署合约后测试） |

worker 的 5 个测试都在本地 anvil 链上实际执行：

1. 走完项目全流程：注册 → 审核 → 工厂部署 → 募集 → 两位投资者认购 → 结算 → 上线 → 转让。核对数据库中的状态、持仓、认购记录。
2. 跑一次真实分配，确认链上算出的净额、费用、余数和 TypeScript 镜像完全一致。
3. 对账干净时通过。故意改坏一条持仓后，能报出持仓和总量两类问题。
4. 模拟链重组（快照后转账，再回滚链并出新块），索引器能检测到、回退，并重建出与链上一致的数据。

API 测试覆盖了这些情况：

- 其他域名、其他链 ID、他人钱包签名、nonce 重复使用，都无法登录。
- 投资者只能看到自己的持仓。
- 非员工、或链上没有对应角色的员工，都不能进后台。
- 不平衡的报告被拒绝，重复报告被拒绝。
- 提交人审核自己的报告被拒绝；报告未上链时不能审核。
- 分配预览按快照块的余额计算：转让前是 60/40，转让后是 50/50。
- 超出报告金额、快照块超出范围、对账未通过时，都拒绝准备分配。
- 准备的 `proposeBatch` 交易里，持有人地址按升序排列。
- KYC 回调：签名错误、时间过期、重放、未知服务商都被拒绝。

另外还做了这些检查：

- `pnpm -r build` 编译成功。
- 用编译后的 API 启动服务，`/api/v1/health` 和 `/api/v1/projects` 正常返回。

## 3. 与第一阶段设计的差异

- 文档核验接口暂时是 `GET /projects/:id/records/:recordId/verify?hash=`，直接按链上记录 ID 核验。
- 任务队列没有用 BullMQ，改为单进程轮询加 Redis 租约，逻辑更简单，效果相同。
- 项目展示信息（标题、品牌、型号）单独放在 `project_meta`，不与链上数据表做外键。这样链重组重建时不会误删。

## 5. 本地运行

```bash
docker compose up -d                  # PostgreSQL + Redis（或使用本机已有的服务）
cp .env.example .env                  # 填写数据库、RPC、合约地址、SESSION_SECRET
pnpm install
pnpm --filter @roboshare/db migrate   # 建表
pnpm build
node apps/worker/dist/main.js         # 索引器
node apps/api/dist/main.js            # API，默认端口 4000
DATABASE_URL=<以 _test 结尾的库> pnpm test
```

worker 测试需要本机安装 Foundry（anvil、forge）。
