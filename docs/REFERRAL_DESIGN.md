# RoboShare 推广奖励（邀请返佣）机制设计 · 草案

状态：R-1、R-2 已于 2026-10-10 确定，已实现（见 §7）。2026-10-11 改为两级（见 §8），2026-10-27 改为三级、按分润总额计算（见 §10，取代 §2 和 §8 的比例）。部署后默认关闭。
日期：2026-10-10

---

## 1. 先说清楚：平台的钱从哪里来

查了现有合约，平台（运营方）目前**只有一种收入**：

- 认购时：投资者付的 USDT 全部进 `OfferingManager` 托管，募集成功后**全额转给发行方金库**（`OfferingManager.sol` settle）。平台在认购环节**一分钱都不收**。
- 分配时：每期利润分配，`RevenueDistributor` 按持有人档位扣 10%–20% 的分级手续费，转给 `feeRecipient`（D-8：没有单独管理费）。

所以推广奖励只能从下面三个口袋里出：

| 口袋 | 说明 | 结论 |
|---|---|---|
| A. 平台的分级手续费 | 被邀请人每期分配时平台收到的手续费，拿出一部分给邀请人 | **推荐**。不动投资者本金和收益池，平台有收入才付奖励 |
| B. 平台自有资金（营销预算） | 被邀请人认购成功后，平台先垫钱付一笔一次性奖励 | 可选。拉新效果好，但平台要先掏现金，收入要等第一次分配后才有 |
| C. 发行方募资款 | 从投资者认购款里扣佣金 | **不建议**。等于用投资者本金付销售佣金，必须在募集条款里披露，而且法律风险最大 |

## 2. 推荐方案（默认）

**单层邀请 + 手续费分成 + 链上领取**

1. **单层**：只有"邀请人 → 被邀请人"一层。被邀请人再邀请别人，原邀请人**拿不到任何东西**。不做团队、等级、多级返佣。
2. **奖励 = 被邀请人产生的平台手续费的 20%**，期限 **12 个月**（从被邀请人第一笔认购算起），按 USDT 结算。
   - 例子：被邀请人持有某项目 4 个单位，某期分到总额 400 USDT，档位 20%，平台手续费 80 USDT → 邀请人拿 16 USDT，平台留 64 USDT。
   - 被邀请人自己**不受任何影响**：本金、收益、手续费档位都不变。
3. **绑定规则**
   - 被邀请人通过邀请链接进入 DApp，**第一次认购时**在链上记录邀请人（见 §4）。之后不可更改，先绑先得。
   - 不能邀请自己；邀请人本身必须是已通过资格白名单的地址（目前由运营方手动设置）。
   - 绑定在整个平台生效（跨项目），12 个月窗口只看时间。
4. **结算**：每期分配批次批准后，后端按链上事件算出每个邀请人的应得金额，生成 Merkle 根，平台从手续费钱包往一个新的 `ReferralRewards` 合约充值，邀请人在 DApp 里自己点"领取"（和现在领收益一样的 pull 模式）。
5. **风控**
   - 退款的认购（募集失败或未达最低单位）不产生奖励，因为根本没有手续费。
   - 奖励比例、期限由治理（2/3 多签，签名后立即生效）设置，改动只对新绑定生效。
   - 暂停（pause）时领取也暂停，和 D-21 一致。
   - 合约里不存在"从投资者或分配池扣钱"的路径，奖励合约只能花平台自己充进去的钱。

## 3. 可选方案

**B. 一次性认购奖励**：被邀请人的认购在项目募集成功（settle）后，邀请人一次性拿认购金额的 **1%**（由平台营销预算支付，单人/单项目设上限）。募集失败退款则不发。适合启动期拉新，代价是平台先垫现金。

**A + B 都要**：前期拉新用 B，长期用 A。成本最高。

**被邀请人优惠**（默认不给）：比如首次认购减免一期手续费。会让同一项目里的投资者待遇不一样，需要在募集条款里披露，建议先不做。

## 4. 合约改动范围（确认后实现）

尽量不动已经测好、审过的核心合约：

- `SubscriptionRouter`：新增 `subscribeWithReferrer(projectId, units, maxCost, referrer)`，只做两件事：首次认购时记录 `referrerOf[investor]`，发出 `ReferralBound` 事件；资金流向**完全不变**。原 `subscribe` 保留。
- 新合约 `ReferralRewards`：Merkle 领取 + 平台充值 + 暂停；没有提取投资者资金的能力。
- 后端：监听 `ReferralBound` 和分配批次事件，计算奖励并生成 Merkle 树；管理后台加"推广奖励"页面。
- 前端：邀请链接、我的邀请、可领取奖励。
- `RevenueDistributor`、`OfferingManager`、代币合约：**不改**。

## 5. 法律风险（必须看）

> 以下是风险提示，不是法律意见。主网上线前必须由律师确认。

- **多级返佣 = 传销风险**。在中国，按发展人员层级（三级及以上）计酬、以发展下线为主要收益来源，可能被认定为传销；配合"收益权代币"募资，还可能叠加**非法集资**。所以本方案最多两级，不做第三级（见 §8）。
- **即使单层，"按卖出金额拿佣金"也可能被视为无牌证券经纪/销售**。我们的代币是"利润分配的合同经济权利"（D-1），在美国（SEC）、香港（SFC）、新加坡（MAS）等多数法域很可能被认定为证券；向不持牌的个人支付与成交挂钩的佣金，是监管重点打击的行为。方案 B（按认购金额付佣金）比方案 A 更直接触碰这一点。
- **目前没有 KYC**：无法核实邀请人身份和所在法域，也很难防止一个人用多个钱包自己邀请自己（目前靠运营方手动白名单缓解）。
- **结论**：测试网可以先上线这个功能做演示；**主网开启推广奖励前**，应和现有 M6 关口（审计、法律、KYC、书面批准）一起，由律师确认奖励形式、对象（是否只限持牌渠道/合作机构）和披露文本。合约里加一个总开关，默认关闭。

## 7. 实现说明

### 合约

- `SubscriptionRouter.subscribeWithReferrer(projectId, units, maxCost, referrer)`：资金流与 `subscribe` 完全相同。只在调用者**第一次**通过路由认购时绑定邀请人；邀请人必须本人认购过，不能是自己或零地址；不满足条件时忽略邀请人而不是让认购失败。绑定发出 `ReferralBound(investor, referrer, shareBps, expiresAt)`，把当时的条款写进事件。
- `SubscriptionRouter.setReferralTerms(enabled, shareBps, window)`：仅治理 Safe 可调用；`shareBps` 上限 5000，`window` 1 秒至 3650 天。默认关闭、2000（20%）、365 天。
- `ReferralRewards`：Merkle 累计领取。叶子 = `keccak256(bytes.concat(keccak256(abi.encode(account, cumulative))))`；每次发布新根覆盖旧根，领取时只付差额；任何人都可提交，奖励总是发给 `account`。`claimsEnabled` 默认关闭，仅时间锁可开；暂停时不能领取（D-21）；时间锁可以取回合约余额。
- 部署脚本同时部署 `ReferralRewards`（管理员 = 治理 Safe，发布根 = 运营钱包），并核对两份合约都处于关闭状态。

### 信任假设

- 运营钱包（`ROOT_SETTER_ROLE`）决定奖励根内容，可以发布错误的根。奖励合约里只有平台自己充进去的钱，不涉及投资者资金；建议每期只充值当期需要的差额（控制台会显示"合约至少需持有"）。
- 计提规则在链下执行：每个分配批次被批准时，对每个有有效绑定的被邀请人，奖励 = floor(该笔分配的平台手续费 × shareBps / 10000)。批准时绑定已过期，或邀请人资格无效（冻结、撤销、过期），该笔不计提，之后也不补发。

### 运营流程

1. 法律确认后，治理在控制台"邀请奖励"页生成 Safe 提案，一次开启路由绑定和奖励领取。
2. 每期分配批准后，运营在同一页点"生成并发布奖励根"，用运营钱包签名。
3. 平台手续费钱包向 `ReferralRewards` 转入页面显示的差额。
4. 邀请人在 DApp"我的资产"里复制邀请链接、查看奖励并领取。

### 后端与前端

- 数据表：`referral`、`referral_accrual`、`referral_root`、`referral_claim`（链上事件投影，重组时重建）和 `referral_tree`（运营生成的树，不随重建删除）。
- 接口：`GET /me/referrals`、`GET /admin/referrals`、`POST /admin/referrals/root`（运营）、`POST /admin/referrals/terms`（治理，返回 Safe 提案）。
- 只有在链上根已生效且证明自检通过时才返回可领取的证明。
- DApp 在落地页记录 `?ref=` 参数；功能关闭时邀请面板和认购页提示都不显示。

## 8. 两级奖励（2026-10-11）

Charlene 于 2026-10-11 要求把推广改成两级（"2级代理"）。

- **一级**：不变。被邀请人每期分配产生的平台手续费 × 绑定时的 `shareBps`（默认 20%）。
- **二级**：邀请人的邀请人，拿同一笔手续费的 `REFERRAL_LEVEL2_SHARE_BPS`（默认 5%，`packages/shared/src/referral.ts`）。平台每笔手续费最多付出 25%。
- **期限**：两级都按被邀请人的绑定窗口（12 个月）计算。
- **资格**：每一级的领取人都要在批次批准时资格有效，否则该级不计提，也不补发。
- **没有第三级**：再往下的人不产生任何奖励。绑定只发生在第一次认购，且邀请人必须已认购，所以关系不会成环。
- **合约不改**：链上只记录一层绑定；第二层由后端按"邀请人的邀请人"推算，和一级一样进入 Merkle 根。二级比例写在代码里，改动需要发版；主网审计前可以考虑改为链上治理参数。
- `referral_accrual` 增加 `level` 列（1 或 2），主键包含 level。
- DApp 推广中心分别显示一级成员、二级成员（含"由谁邀请"）和每笔收益的级别。

**法律**：两级仍在"三级及以上"的传销认定门槛之下，但更接近"发展下线"，且按成交拿佣金的无牌经纪风险不变。主网开启前必须由律师确认，总开关默认关闭。

## 9. 推广团队（2026-10-26）

Charlene 于 2026-10-26 选择"统一结算 + 团队后台"（当时保持两级；2026-10-27 改为三级，见 §10）。

- **团队** = 一个团队长钱包 + 一个团队码（2–16 位字母或数字），由运营在控制台"推广团队"页创建。团队长和团队码创建后不能改，只能改名称。
- **团队链接**：投资者网站 `/t/团队码`，跳转到 `/?ref=团队长地址`。团队成员用自己的个人邀请链接邀请的人，也归入同一团队。
- **归属规则**：不单独存成员表，完全按链上 `ReferralBound` 绑定推算：一个钱包属于沿邀请人链向上最近的团队长的团队（`packages/shared/src/team.ts` 的 `placeInTeams`）。链上绑定在首次认购时写入、永不更改，所以**一个人不会被两个团队重复计算，也不会换队**。
  - 新建团队时，如果团队长钱包已经在别的团队下面，拒绝创建（`LEADER_IN_TEAM`），新团队不能抢已有团队的成员。
  - 团队长必须自己认购过至少一次，链上才接受他作为邀请人；控制台会标出"未认购，链接暂不生效"。
  - 推广开关（`referralsEnabled`）关闭时链上不记录邀请关系，团队也就没有新成员。
- **结算不变**：团队只用于统计和展示。奖励按 §10 的三级规则（只从平台手续费出），全部进同一棵 Merkle 树、同一个 `ReferralRewards` 合约，每个人在 DApp 自己领取。团队长不因"团队"身份多拿任何奖励。
- **团队后台**：控制台 `/leader`，团队长用自己的钱包签名登录（不需要运营账号、链上角色或验证器），只读查看本团队的成员、层级、认购额、手续费和邀请奖励。平台运营在"推广团队"页可以看到所有团队。
- **接口**：`GET /teams/:code`（公开，解析团队链接）、`GET /team/me`（团队长）、`GET/POST /admin/teams`、`GET/PUT /admin/teams/:id`（创建和改名需运营角色，写入审计日志）。
- **合约不改**。

**法律**：团队分组本身不改变计酬方式，但"团队长 + 下线"的组织形式更容易被认定为发展下线。主网开启推广前，律师审查时要一并说明团队功能。

## 10. 三级推广 + 收益七三分（2026-10-27）

客户需求经 Charlene 转达，她在 2026-10-27 选择方案"甲"（对比见项目文件 docs/REFERRAL_3LEVEL_PROPOSAL.md）。

- **收益七三分**：2026-10-27 之后部署的项目，平台分成统一 30%（`FeeTiers.defaultTiers` 单档 3000 基点），投资者拿 70%，与持有份数、运营期无关。已部署的项目保留部署时的分档费率（链上不可改）；索引器把每个分配合约的 `tiers()` 记到 `project.feeTiers`，预览和网站展示按实际档位。
- **三级奖励**：被推荐投资者每期分润**总额**（扣平台分成前）的 10%（直推）、5%（二级）、3%（三级），太阳线，直推人数不限，第四级起没有奖励（`REFERRAL_LEVEL_BPS`）。
- **资金来源**：全部从平台那 30% 里支付，**投资者的 70% 永远不动**，有没有推荐人投资者到手都一样。例：分润 1000 → 投资者 700，A1 100，A2 50，A3 30，平台留 120。
- **封顶**：每笔奖励合计不超过该笔平台手续费（按一级、二级、三级顺序扣），旧的低费率项目不会让平台倒贴（`referralRewards`）。
- **期限**：三级都按被推荐人的绑定期（默认 12 个月，治理可调到最长 3650 天，只影响新绑定）。
- **比例写在代码里**：链上 `ReferralBound` 记录的 shareBps 不再决定金额；治理提案只设开关和奖励期。
- **其余不变**：被冻结的领取人该级不计提也不顺延；Merkle 领取、统一金库、团队功能（§9）不变。`referral_accrual` 新增 `gross` 列。

**法律（必须看）**：按发展人员层级计酬、达到三级，是中国"组织、领导传销活动罪"的立案层级标准；奖励按下线的投资收益计算，风险高于按消费计算，还可能叠加非法集资和无牌证券销售。测试网可以演示；**主网总开关默认关闭，律师书面确认后才能开启**。网站和推广材料不得承诺固定收益。
