# 第二阶段报告：核心合约与测试

日期：2026-10-09　分支：`phase2/core-contracts`

## 1. 本阶段完成了什么

代码位于 `contracts/`（Foundry 项目）。

| 合约 | 作用 | 部署方式 |
|---|---|---|
| `IdentityRegistry` | 投资者资格（KYC 结果）、冻结、过期 | 全平台一个 |
| `AssetRegistry` | 项目登记与状态机（DRAFT → … → CLOSED） | 全平台一个 |
| `AuditRegistry` | 审计报告、单据哈希登记，提交人 ≠ 审批人 | 全平台一个 |
| `SubscriptionRouter` | 用户只授权一次 USDT，之后按份数购买 | 全平台一个 |
| `ProjectFactory` | 为已审核项目一次性部署下面三个合约 | 全平台一个 |
| `RwaShareToken` | 限制转让的份额代币，固定 100 份，0 位小数，带历史快照 | 每个项目一个 |
| `OfferingManager` | 募集托管、结算、失败退款 | 每个项目一个 |
| `RevenueDistributor` | 按快照计算分配、扣分档费率、持有人自己领取 | 每个项目一个 |

部署脚本 `script/Deploy.s.sol`：

- 主网（chainId 56）必须设置 `CONFIRM_MAINNET=I_UNDERSTAND_THIS_IS_MAINNET` 和真实 `USDT` 地址，并检查 USDT 小数位为 18。
- 非主网未提供 USDT 时部署 TEST-ONLY 的 MockUSDT（该合约在 56 链上会直接报错）。
- 部署后所有管理权限交给 24 小时时间锁，时间锁的提案和执行权只给多签 Safe（D-16）。部署者自动放弃权限，脚本最后逐项核对角色。

## 2. 测试结果（实际运行）

工具：Foundry 1.5.1、solc 0.8.30、OpenZeppelin 5.4.0、forge-std 1.9.7。

- `forge test`：12 个测试套件，**91 个测试全部通过，0 失败**。
- `FOUNDRY_PROFILE=ci forge test`：模糊测试 10,000 轮，不变量测试 256 轮 × 128 深度，**91 个全部通过**。
- `forge script script/Deploy.s.sol`（本地模拟，不连任何链）：成功，所有部署后检查通过。
- `forge build --sizes`：所有合约都低于 24KB 上限。

主要 gas（单元测试中位数）：认购 `subscribe` 约 18.1 万；结算 `settle` 约 55 万；提交分配 `proposeBatch`（6 位持有人）约 49.6 万；审批 `approveBatch` 约 19.4 万；领取 `claim` 约 3.6 万；部署一个项目 `deployProject` 约 654 万。

### 已覆盖的要求测试

- 未认证钱包不能接收份额；冻结钱包不能转出。
- 超过 100 份上限的铸造被拒绝；不能销毁。
- 收益计算：主提示例子（10 份、15% 费率、可分配 10,000 → 850）和 TOKENOMICS §4.4 例子（总费用 1,240，净额 8,760）完全一致。
- 余数（dust）结转到下一批；只有项目关闭后才能清扫。
- 同一报告重复分配或超额分配被拒绝；空批次、零金额、持有人列表不完整、未排序、重复都被拒绝。
- 快照块不能早于募集完成，也不能是未来块；快照后的转让不影响本期分配。
- 未审批、已被修订替代、属于其他项目的报告不能用于分配。
- 提交人不能自己审批（资产审核、审计报告、分配批次三处）。
- 重复领取被拒绝；冻结钱包暂时不能领取，解冻后可以领取（D-13）。
- 暂停后认购、结算、退款、领取都被阻止（D-21）。
- 无权限账户不能执行管理操作。
- 收手续费的代币（fee-on-transfer）付款被拒绝；恶意代币的重入攻击被重入锁挡住。
- 向托管合约直接打钱不会卡住认购。

### 不变量（随机操作序列后始终成立）

- 分配合约余额 = 尚未领取总额 + 结转余数。
- 代币总量不超过 100，募集完成后恒为已发行份数。
- 路由合约永远不留存 USDT。
- 募集托管合约余额 ≥ 托管记账金额，且托管金额 = 用户实际付款总额。
- 每次分配：净额 + 费用 + 余数 = 资金池，且余数 < 持有人数。

## 3. Slither 静态分析（slither-analyzer 0.11.3）

运行 `slither . --filter-paths "lib/|test/|script/"`，排除信息级后共 20 条，中高级 7 条，逐条判断如下：

| 发现 | 判断 |
|---|---|
| `approveBatch` 从任意地址 `transferFrom` | 不是问题。来源是部署时固定的项目金库地址（不可修改），且必须由第二人审批后才执行。 |
| `settle` 在铸币外部调用后写状态 | 不是问题。被调用的是本项目自己的份额合约，函数有重入锁，且铸币不回调外部地址。 |
| 局部变量未初始化（`prev`、`proceeds`） | 误报，Solidity 默认为 0，正是需要的初始值。 |
| 忽略检查点 `push` 返回值 | 有意为之，返回值是旧值，不需要。 |
| 循环内外部调用、使用时间戳比较、事件在外部调用后发出 | 低风险，已知且可接受：持有人上限 100，时间只用于募集开始/结束这种以天计的窗口。 |

## 4. 与第一阶段文档的差异（实现时的调整）

- 分配资金的来源固定为项目金库地址（部署时写入，不可更改），不再作为参数传入。
- 费用接收地址和金库地址在每个项目内都不可修改；如需变更，需新项目。
- `AuditRegistry` 强制同一项目的财务报告期间不重叠，并且同一期间只能有一份有效报告（修订会替代旧版）。
- 托管合约收到额外转账（捐赠）时不会报错，多出的钱不计入任何人的认购。
- `ProjectFactory` 使用三个小的部署辅助合约，以保持在合约大小上限内。
